## Findings

1. **P1 — Generated columns can become mandatory import inputs.** `src/hooks/useImportTableData.ts:155` (integration: `src/screens/connection/table/MainTableDataPane.tsx:491`). The helper trusts `auto_generated`, `is_identity` and `extra`, but the actual SQL Server metadata queries/loaders populate none of those for identity/computed columns: `src/lib/queries/sql/columns.ts:155`, `src/lib/queries/sql/tableStructure.ts:107`, `src/lib/table-data/loaders/sqlLoader.ts:418`. An ordinary `id INT IDENTITY PRIMARY KEY` therefore arrives as NOT NULL with no default and is marked required. A CSV containing only writable columns now cannot be imported; mapping the identity column instead requires a value SQL Server normally rejects. This is a new blocking regression. PostgreSQL NOT NULL generated columns also lack a generated-column flag in the current metadata projection. **Fix:** carry authoritative generated/identity metadata through the engine adapters into the import helper; do not infer it solely from defaults or PK/type heuristics. **Regression test:** use production-shaped SQL Server metadata for identity, computed and ordinary required columns; import with generated columns skipped and assert Import is enabled. Cover PostgreSQL generated/identity, MySQL auto-increment/generated, and SQLite rowid versus genuinely required PK columns.

2. **P1 — The new failure banner incorrectly promises that no writes occurred.** `src/components/modal/ImportTableDialog.tsx:251`. Every error is labeled “Nothing was imported.” However, the unchanged D1 implementation executes statements individually without rollback (`src-tauri/src/engines/runtime/connection_ops.rs:226`): if row 1 succeeds and row 2 fails, row 1 remains inserted. The new banner now tells the user the opposite, making a manual retry liable to duplicate data. The hook also catches `onSuccess()` failures after the import has committed (`src/hooks/useImportTableData.ts:313`), so a rejected post-import callback is not evidence of rollback either. **Fix:** use neutral failure wording unless rollback is known, and distinguish a committed import followed by refresh failure. Do not silently alter existing transaction behavior to fix this presentation issue. **Regression test:** simulate a D1 second-statement failure after a first successful write and assert no zero-write promise; separately resolve the importer and reject the refresh callback, asserting the UI preserves the committed result and reports refresh failure.

3. **P2 — Preview and execution still disagree on CSV records and values.** `src/utils/csv.ts:112`; `src-tauri/src/engines/csv_import.rs:160`, `:182`. Independent probes against installed Papa and the actual Rust parser confirmed: `id;name\n1;"a;b"\n` yields an extra empty preview row but only one imported data row; `name\n""` previews one valid empty-string record but Rust drops it entirely; leading LF blank lines are retained by Papa but removed by Rust, shifting both the header and the new “data row N” interpretation; BOM is stripped by Papa but retained in Rust's first cell when importing without headers. This is a **pre-existing parser defect carried through the touched parser**, not caused by adding the delimiter field. Delimiter forwarding is correct, but delimiter parity alone does not meet the requested parity check. **Fix:** define one record/BOM/empty-line policy for preview and execution, retain explicitly quoted empty records, and reject malformed quotes consistently. **Regression test:** run identical fixtures through both parsers for all four separators, escaped quotes, delimiter inside quotes, LF/CRLF/CR, embedded newlines, trailing newline, leading/interior blank lines, BOM with/without headers, quoted empty final records and unterminated quotes. Assert values, record counts, validation row indices and statement-error row indices agree.

4. **P2 — Standalone export preparation errors still escape the inline-error flow.** `src/screens/connection/export/StandaloneTableExportHost.tsx:45`. Metadata-load errors still call native `showMessage` and then `close()`, clearing the target. The changed ExportTableDialog only handles errors after the host reaches `ready`; an unavailable metadata query therefore bypasses the approved inline error/retry experience. This is an **existing flow omitted from the approved polish**, rather than a newly introduced execution bug. **Fix:** render the failed preparation state inline in the host, retain its target, and expose the hook's existing `retry` action; retain quiet cancellation and stale-request guards. **Regression test:** reject metadata loading, assert an inline alert and retry without a native message or target clearing, then cover successful retry, cancellation during preparation, and target replacement while a request is pending.

### Remaining findings

1. **R2-1 · P1 — Engine allowlist still promises rollback where writes can persist.** `src/hooks/useImportTableData.ts:195` (banner: `src/components/modal/ImportTableDialog.tsx:261`). MySQL/MariaDB are unconditionally classified as atomic, but `connection_ops.rs:166-179` only issues START TRANSACTION/ROLLBACK; it never verifies table storage-engine support. A MyISAM table with a successful first insert and duplicate-key failure on the second retains the first row despite ROLLBACK, while this UI says “Nothing was imported.” Retrying can duplicate saved rows. [MySQL documents that nontransactional tables are unaffected by ROLLBACK](https://dev.mysql.com/doc/refman/8.4/en/nontransactional-tables.html). Also, errors returned from COMMIT on transactional engines do not necessarily prove rollback: a lost acknowledgement can follow a successful server-side commit, and rollback errors are currently discarded. **Fix:** use neutral/unknown-outcome wording unless the backend explicitly confirms a zero-write outcome; at minimum remove unconditional MySQL/MariaDB guarantees and treat commit/transport/rollback failures as uncertain. Preserve existing transaction behavior. **Regression test:** simulate a MyISAM second-row rejection after a persisted first row and a COMMIT acknowledgement failure after persistence; neither may render the zero-write banner. Also retain confirmed rollback and D1/post-import-reload cases.

2. **R2-2 · P2 — Parser parity copies silent quote deletion instead of validating field boundaries.** `src/utils/csv.ts:126-132`; `src-tauri/src/engines/csv_import.rs:179-181`. Every non-escaped quote toggles quoted mode regardless of position. Independent probes against the actual TS module and an unchanged extracted Rust function both accept `name\na"b"c\n` as `[["name"], ["abc"]]`, silently deleting literal quote characters; `name\n"a"oops\n` is accepted as `aoops`. Installed Papa previously displayed `a"b"c` unchanged, so the new preview now silently normalizes the same malformed input the backend already mishandled. An unmatched quote in an otherwise unquoted value (`12" widget`) now fails during file loading. The existing backend defect is carried through the touched parser, and round 1's malformed-quote requirement remains incomplete. **Fix:** track field-start / quoted-field / closed-quote states in both parsers. Either preserve quotes in unquoted fields under an explicitly supported permissive policy or reject them; reject trailing non-delimiter characters after a closing quote. Do not silently delete characters. **Regression test:** mirror fixtures for balanced and unmatched interior quotes, trailing characters after closing quotes, legitimate doubled quotes and embedded newlines across all four separators; assert exact values or matching rejection before importer invocation.
