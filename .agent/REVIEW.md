## Findings

1. **P1 — src/screens/connection/ConnectionScreen.tsx:958–963; src/components/modal/SaveChangesDialog.tsx:314–316 — Busy/error capture ends before every save job finishes.** `saveChanges` starts patch, new-table and object jobs concurrently and awaits `Promise.all` (useConnectionActions.ts:869–885). A new-table/object rejection settles that promise immediately while sibling jobs continue. The wrapper clears saveErrorsRef and the dialog releases savingRef; Retry can start another patch/new-table save while the original still executes. Late sibling errors go to the old native message path instead of the dialog, and the wrapper drops the thrown error whenever another message was already reported. **Fix:** keep the save lifecycle locked until every started job settles; aggregate all reported/rejected outcomes without losing distinct errors. Preserve per-job success consumption and existing safety gates. **Regression test:** mount the real screen/save orchestration with deferred patch/new-table/object jobs; reject one early, verify busy and error capture persist until all settle, prevent retry/close/duplicate execution, and show every failure once.

2. **P2 — src/components/modal/SaveChangesDialog.tsx:485 (`if (!hasChanges)`), integrated with ConnectionScreen.tsx:972 — A post-write failure can leave an invisible, still-open review.** Patch saves clear patches before refresh; new-table saves remove drafts before refresh/openTable. If a subsequent awaited refresh/open throws, the wrapper rejects and retains showSaveDialog, but hasChanges is already false and the dialog returns null, hiding its error and controls. A fully successful write must not be presented as unsaved work or retain a hidden modal state. **Fix:** distinguish write failures from refresh/navigation failures; close after successful writes and surface refresh failures accurately, or render a dismissible completion/error state even with no remaining changes. **Regression test:** successful patch/new-table write followed by rejected reload/open; assert no replayable work, no hidden showSaveDialog state, and visible accurate feedback. Also cover partial success with remaining failed drafts.

3. **P2 — src/components/modal/saveReviewSql.ts:17,27–31 — DROP COLUMN detection matches literals/quoted names.** The regex scans arbitrary text after ALTER TABLE, so valid generated ADD/MODIFY statements with a default containing ` DROP COLUMN x`, or a quoted table name containing that phrase, become destructive and claim a column is dropped. Read-only harness against the actual transpiled module returned `destructive` / `drops 1 column` for both cases. **Fix:** inspect tokens outside quoted identifiers, literals and comments, or derive destructive intent from structured patches; retain dialect-specific generated DROP COLUMN support. **Regression test:** feed actual PostgreSQL/MySQL generated ADD/MODIFY SQL containing these values/names and assert no destructive warning; retain true drops across engines. Include ClickHouse ALTER TABLE DELETE: currently classified structure, despite the patch delete count correctly enabling the overall warning.

4. **P2 — src/components/modal/SaveChangesDialog.tsx:342–350 — Mod+Enter also reaches application shortcuts.** The document listener calls preventDefault but never stops propagation. useConnectionShortcuts listens on window and does not inspect defaultPrevented; user bindings or snippet hotkeys on Mod+Enter can therefore run another action alongside Save. Shift/Alt variants also trigger Save because extra modifiers are not checked (including the editor's Mod+Shift+Enter chord). When destructive/saving, the chord is not consumed at all. **Fix:** match the exact intended chord, contain modal keyboard events before background handlers, and ensure Monaco cannot execute behind an open review. **Regression test:** render dialog with real connection shortcut hook and a Mod+Enter binding/snippet, dispatch bubbling events from focused controls, and assert only one intended action; cover destructive, disabled, saving and Shift/Alt variants, plus editor focus behind the dialog.

5. **P2 — src/components/modal/SaveChangesDialog.tsx:325 — No-statements saves remain enabled unless there are only object notices.** A patch map can contain pending but non-executable/no-op structure or constraint entries; generateSqlFromPatches deliberately returns no SQL for some such edits. The dialog explicitly renders its zero-statements warning, yet canConfirm remains true, initially focuses Save and accepts Mod+Enter. This violates the approved “nothing to run” guard. **Fix:** require at least one executable statement/operation for confirmation and keyboard submission, alongside generation-error and busy guards. **Regression test:** nonempty patch map whose generator returns [], no object notices; assert disabled Save, zero onConfirm calls for click/Mod+Enter and appropriate initial focus.

Synthetic combined ALTER with an ordinary trailing-backslash default followed by a true DROP is also currently classified structure; do not assume this scanner provides a general safety boundary.
