## Goal And Visible Result

- Backup, restore and SQL dump import (menu, table pane, sidebar) show a modal with title, phase, progress bar, counts and a **Cancel** button (disabled, with the reason, where cancel is not possible).
- Cancel never publishes a partial backup and never damages an existing file at the destination.
- A cancelled or failed PostgreSQL restore is never committed; every message states exactly what is known about rollback (D7).
- A cancelled restore on another engine stops at a statement boundary and reports settled counts (D10).
- While a job runs, closing its tab, window or the app is refused with a message (D8).

## Decisions

- D1 UI — modal, like the table import/export dialogs.
- D2 Scope — database backup, database restore, SQL dump import from the table pane and the sidebar. CSV import/export unchanged.
- D3 Non-transactional cancel — the user never cancels a running statement; the run stops at the next statement boundary (detail D10).
- D4 Backup progress — per-step bar ("Table 3 of 12"), rows written shown as a count; no row percentage.
- D5 Success — modal closes; existing success toast; existing info toast when statements were skipped. Committed but schema refresh failed: warning in the modal saying the restore **was committed** and only the refresh failed.
- D6 Blocking — the modal blocks its window; no background mode.
- D7 PostgreSQL wording (simplification D) — one rule for every path (cancel, statement failure, safety stop, confirmation), chosen by evidence:
  - no statement was sent: "Nothing was run.";
  - `ROLLBACK` answered by the server: "The transaction was rolled back.";
  - the session was closed without a ROLLBACK answer (user cancel, cancel/rollback failure, connection lost): "The transaction was not committed. The server rolls it back when its connection closes.";
  - COMMIT without answer: existing `COMMIT_OUTCOME_UNKNOWN` message, unchanged.
  - neither a ROLLBACK answer nor a confirmed close (cancel and fallback both failed): the `cleanup-unconfirmed` text in "Cancel state and precedence".
  - which case applies is decided only by the evidence rules in "Cancel state and precedence".
  - Whenever at least one statement was sent, add: "Sequence changes (nextval, setval) and effects outside the database (for example dblink or extensions) are not undone."
  - The confirmation before a PostgreSQL restore replaces "nothing is changed" with: "They run in one transaction: if one fails or the run is cancelled, it is not committed. Sequence changes and effects outside the database are not undone. Once committed, it cannot be undone."
- D8 Close/quit (simplification A) — while a dump job is **active** (from registration before the file dialog until its cleanup has settled; a retained result summary, D15, is not active), closing the job's tab, any window holding a job, or quitting the app is **refused** with "A backup or restore is running. Cancel it and wait for it to finish, then close." No automatic cancel, no waiting close. Unsaved-change prompts are not shown first (the refusal is checked before any discard/save step).
- D9 File integrity + compression (simplification C) — backups are written to an exclusive temp sibling and published; the destination is untouched unless publication succeeds. Compression is not interrupted: Cancel during it shows "Cancelling — waiting for compression to finish", then the temp is never created/published. Publication is not cancellable; success is reported only after publication succeeds.
- D10 Non-transactional cancel — Cancel sets a stop request; the current statement finishes; no further statement starts. The confirmation opens only **after** the current statement has settled, showing settled counts: "N of M statements ran and stay in the database. Stop here?" Stop → terminal "stopped". Continue → resume. Counts: completed, skipped, unknown (failed by timeout/transport: "may be partly applied").
- D11 One job (simplification B) — at most **one dump job in the whole app** at a time (backup, restore or import). A second start is refused: "Another backup or restore is running." The modal shows that single job, in the window it was started from.
- D12 Terminal UX — Esc, × and outside click ignored while running; only Cancel cancels. Cancelled backup: modal closes, info toast "Backup cancelled. No file was written." Cancelled/stopped/failed restore or import: outcome in the modal with Close. Declining the initial restore confirmation ends the job quietly (no modal message). Errors before the job is registered keep `showMessage`.
- D13 Privacy — every dump query, stream and statement uses `internal: true`; progress detail is transient in the job store, cleared when the job's modal closes, never persisted or logged.
- D14 Native prompts first (E) — the job is registered (slot taken) before the file dialog, but the progress modal opens only after the file dialog, the restore confirmation and Touch ID have all completed. While those native prompts are open there is no Cancel button: the prompt itself is the way to cancel (dismissing it ends the job quietly as `abandoned`). A positive prompt result is accepted only if the job is still current and its origin still holds (checked synchronously right after the prompt resolves); otherwise it is dropped.
- D15 Retained results (F) — results the user must read (failed, stopped, cancelled restore/import, committed-refresh-failed, commit-unknown, temp-file not removed) stay in the modal until the user presses Close. While such a summary is open, a new dump job is refused: "Close the previous backup/restore result first." Closing the tab, window or app is **allowed** while only a summary is open (the job is no longer active); the summary closes with its window.

### Job identity and lifetime (answers R2-5)

- `start` registers the job **before** the file dialog (phase `choosing-file`), capturing `origin` immutably; the active slot is taken then (D11). `start` is refused when another job is active (D11 message), when a summary is open (D15 message), or when the origin's scope is in `closing` (close admitted, see guard). The check and the registration are one synchronous store transition.
- After every await (file dialog, confirmation, Touch ID), the hook checks synchronously that the job is still the current job and its origin still holds (tab exists, same `runtimeConnectionId`, scope not closing); otherwise the job ends as `abandoned` (quiet) and the late result is dropped (D14).
- Component unmount does not end a job (the controller owns it); closing the origin tab is refused while the job is active (D8), so an active job cannot outlive its tab.
- Terminal transition, in order: all owned cleanup settles → outcome computed → `active` cleared and, when the outcome must be read (D15), `summary` set, in one store transition. Success and quiet outcomes set no summary.

### Cancel state and precedence (answers R2-3)

`CancelState = none | requested | accepted | refused(reason) | failed(error)`:

- `requested`: set synchronously by `cancel(jobId)`; the runner starts no new work (no statement, no COMMIT, no compression start, no publication). Duplicate Cancel presses while `requested` are coalesced (one action, one prompt).
- `accepted`: the owned cancel action reported success **with evidence** (PostgreSQL: `sql_session_cancel` returned `Cancelled`, i.e. this call won the session and its teardown completed, or `AlreadyClosedByCancel` — another cancel of the same session won and completed; backup: the stream handle reached `client-disposed` and the snapshot session ended; non-transactional: the user chose Stop).
- `refused(reason)`: an acknowledged refusal, not a failure: PostgreSQL `SQL_SESSION_COMMITTING` (the COMMIT/ROLLBACK owns the outcome). The run continues to its end result; Cancel is disabled.
- `failed(error)`: the cancel call itself rejected (IPC/transport error, or `Unknown` session, below). The runner keeps its job **active**, stops starting new work, and runs the fallback for its kind (PostgreSQL: `sqlSessionEnd(id, false)`; backup: abort stream/snapshot/file session). The outcome is taken from the fallback's actual result. If the fallback also fails, the outcome is `cleanup-unconfirmed` (below).

Not-committed evidence (PostgreSQL), used by D7:

- `rolled-back`: `sqlSessionEnd(id, false)` returned Ok (server answered ROLLBACK).
- `not-committed-closed`: the runner never sent COMMIT for this session (a runner invariant recorded in the run, not inferred from the backend) **and** a teardown of this session was confirmed (`Cancelled`, `AlreadyClosedByCancel`, or `end` returned `SQL_SESSION_ENDED` after the run's own cancel won).
- `nothing-run`: no statement was sent.
- `cleanup-unconfirmed`: neither of the above could be established (cancel and fallback failed, or `Unknown`). Message: "The transaction was not committed by PoliteDB, but closing its connection could not be confirmed. Close the connection or check the server before restoring again." plus the D7 sequence sentence.
- `NOT_FOUND`/`Unknown` session ids and `SQL_SESSION_ENDED` without the run's own winning cancel are never evidence.

Outcome precedence: `commit-unknown` > `committed` (+ refresh failure) > genuine failure that happened **before** `requested` (with its own rollback evidence) > `cancelled` with evidence > `cleanup-unconfirmed`. A failure that arrives after `requested` is reported inside the cancelled/unconfirmed outcome ("Cancelled. Also: …"), never classified as skippable/FK/ignorable and never hidden.

Cleanup attempt group (answers R4-3): each job owns one `CleanupGroup`.

- Every cleanup action launched for the job — the cancel call, its fallback, a user retry, late-resource adoption (late session id, late op id, late subscription) — is registered in the group before it starts, and records its evidence when it settles.
- While a cleanup action is pending, Cancel is **disabled** ("Cancelling…"); a retry is offered only after every registered action has settled without establishing evidence, and the retry is itself registered in the group. So attempts are serialized; there are never two concurrent cancel/fallback calls for one job.
- Terminal waits for the group to be empty (all registered actions settled), then takes the **strongest** evidence recorded (`rolled-back` > `not-committed-closed` > `cleanup-unconfirmed`), computes the outcome and **seals** the job: from then on every callback for this `jobId` is ignored, so a late result can neither weaken the evidence nor overwrite a retained summary.
- The user can choose "Stop trying" on the retry offer: the job ends as `cleanup-unconfirmed` after the group is empty.
- No new job and no close admission for the job's scope until the job is sealed (it is still `active`).

Non-transactional Continue (D10): the confirmation is shown once per `requested`; Stop → `accepted`; Continue → `CancelState` returns to `none` only if the job is still current and the same decision is pending (decision id), then the run resumes at the next statement.

## PostgreSQL Session Cancel (answers R2-1)

- Session gains a teardown completion (`tokio::sync::watch<bool>` or `Shared` future) set once when its connection task is aborted, its client dropped and its entry removed. The session stays in the registry in state `CLOSED` until teardown completes, so `end()` racing a cancel sees `SQL_SESSION_ENDED`, not `NOT_FOUND`.
- Each session records **who closed it**: `closed_by: Cancel | End(commit|rollback) | Forced`, set by the transition winner.
- `cancel(session_id)`: atomic `OPEN → CLOSED`, else `ENDING → CLOSED`. The winner sets `closed_by = Cancel` and runs teardown (abort socket, spawn server cancel, drop client, remove entry, signal completion). A caller that finds `CLOSED` awaits the same completion and returns `AlreadyClosedByCancel` only when `closed_by == Cancel`; otherwise `AlreadyEnded` (closed by end or forced: no not-committed evidence). `COMMITTING` → `Err(SQL_SESSION_COMMITTING)` with no side effects. Unknown id (never registered, or removed after a completed end) → `Unknown`, which is **not** evidence of anything.
- `end()`: if it loses `ENDING → COMMITTING` to a cancel, it returns `SQL_SESSION_ENDED` **without** calling `close()`, after awaiting teardown completion. `close()` (forced) is called only for real end errors (timeouts, failed ROLLBACK/COMMIT I/O) and by `end_for_connection`, and runs through the same once-only teardown with `closed_by = Forced`.
- Return values state only what is known: client-side teardown completed; never "server confirmed rollback" (D7 wording).

## Dump Operation Port (answers R2-2)

- `dumpStatement(connectionId, sql, { timeoutMs })` and `dumpStream(...)` built on `operationExecute` + `operationBus` (not on `runSqlQuery`), returning `{ result: Promise, cancel(): Promise<CancelAck>, settled: Promise<Settled> }`.
- `Settled` states only what the client observes:
  - `server-finished`: the bus delivered the operation's terminal done/error event **and** every chunk consumer already invoked for it has settled;
  - `client-disposed`: the handle stopped listening — subscription removed, timers cleared, in-flight chunk consumers awaited, later chunks/events for this op id ignored (an `invalidated` flag checked at the top of every consumer) — without a terminal event. Server completion is **unknown**; the backend's `operation_cancel` (`dispatcher.rs:22–45`) only requests cancellation and aborts the task without joining it, and the port does not claim more.
- `CancelAck = requested | rejected(error)`; a rejected `operation_cancel` is reported to the runner (`CancelState.failed`), and the handle still disposes the client side.
- **One disposal routine** for every cause — explicit cancel, timeout, init/subscribe failure after dispatch, `operationExecute` rejection, consumer exception, bus error (answers R4-1). In order:
  1. latch `stopping` and call `operationBus.invalidate(opId)` (new, opt-in, used only by the dump port): the bus drops later chunks/events for that op id before caching or delivering them and never recreates its cache entry; it still ACKs them so the backend is not left waiting on flow control while its cancel takes effect. Other bus callers are unchanged. The contract is therefore **no later application consumption or writes**, not "no later transport ACKs";
  2. for every op id already known, call `operation_cancel`; for a pending `operationExecute` or subscription, adopt its result when it arrives and then cancel that id / dispose that subscription;
  3. dispose subscriptions and timers; await chunk consumers already running;
  4. resolve `settled` (`client-disposed`, carrying the original error if any) only after steps 2–3 have all settled, including adopted late results. A rejected `operation_cancel` is reported (`CancelAck.rejected`) but does not block `settled`.
- The bus is initialised (`operationBus.ensureInit()`) before `operationExecute`, so an init failure happens before dispatch; a subscribe failure after dispatch still goes through the disposal routine above.
- Snapshot session end and backup file abort run only after the stream handle has settled (step 4), so no consumer can append after cleanup and no backend stream outlives the snapshot without a cancel request.
- `internal: true` behavior (no analytics) is built in. Existing options (`snapshotId`, `canonicalTextOutput`, batch size, row limit) are passed through unchanged. Unrelated callers keep `runSqlQuery` unchanged.
- Non-transactional statements never get a user cancel (D3). A 120 s timeout cancels via the handle; the statement is counted `unknown` and the run **stops** there (terminal `failed` with counts and "the last statement may still be running on the server or be partly applied"), the schema is refreshed, and no further statement starts. This matches today's stop on non-ignorable errors (`useDatabaseBackup.ts:2004–2025`).

## Backup File Session (answers R2-7)

- A separate small service, not the export registry: `src-tauri/src/backup_file.rs` with commands in `commands/backup_file.rs`. Per-session state machine under a per-session mutex: `Open → Written` (one successful `write(id, bytes)`; a failed write → `WriteFailed`) → `Published`; or any non-published state → `Aborted` / `AbortFailed`.
  - `begin(path)` → exclusive temp sibling (reusing `file_storage::export_create_temp` / `is_export_temp_path`).
  - `write` allowed only in `Open`; a second write → error.
  - `publish` allowed only in `Written` (never after `WriteFailed`, never before a write): sync, rename, destination kept on failure; a failed publish moves to `PublishFailed` and requires `abort`.
  - `abort` from `Open`/`Written`/`WriteFailed`/`PublishFailed`/`AbortFailed` (all non-published states; `Written` is the normal cancel-just-before-publish case, serialized with `publish` by the session mutex): deletes the temp. Success → `Aborted`, session removed. Failure → `AbortFailed`, session **kept** so `abort` can be retried; returns `TEMP_NOT_REMOVED`. `abort` on `Aborted`/unknown → Ok (nothing owned). After a successful `publish` the session is replaced by a **tombstone** `Published` (no file handle, no path kept beyond the session) for the lifetime of the app: `abort`/`write`/`publish` on it → `ALREADY_PUBLISHED` error, so repeated terminal calls stay consistent after the resources are released. Tombstones hold only the session id and state.
- The runner retries a failed abort once; if it still fails, the job ends with a D15 summary "Backup cancelled/failed. A temporary file could not be removed next to the destination." (no quiet toast), then releases that failed-abort session (`forget(id)`, allowed only in `AbortFailed`; it can never remove a `Published` tombstone; it logs nothing and leaves the file). Export behavior is not changed.
- Publication evidence (answers R5-2): `ALREADY_PUBLISHED` returned for this job's own session id (to `abort`, `publish` or `write`) proves the rename happened: the job reports **"Backup written"** (success), never "No file was written" or "temporary file could not be removed". This covers a successful rename whose `publish` reply was lost: the runner's follow-up `abort` hits the tombstone. If neither publication nor abort can be confirmed (transport keeps failing), the job ends with a D15 summary "The backup file's status could not be confirmed: check the destination." — no automatic publish retry, never deleting the destination.

## Progress Model

```ts
type DumpPhase =
  | "choosing-file" | "confirming" | "authenticating"
  | "preparing" | "structure" | "data" | "compressing" | "publishing"   // backup
  | "reading" | "checking" | "running" | "committing" | "refreshing";   // restore/import
type DumpProgress = {
  stepsDone: number; stepsTotal: number;   // monotonic, clamped; 0 = indeterminate
  rows?: number;
  processed?: { completed: number; skipped: number; unknown: number };
  detail?: string;
};
type DumpOutcome =
  | { kind: "succeeded"; skipped: number }
  | { kind: "cancelled"; rollback: RollbackEvidence; counts?: Counts; failure?: string }
  | { kind: "stopped"; reason: "safety" | "user"; rollback?: RollbackEvidence; counts: Counts }
  | { kind: "failed"; message: string; rollback?: RollbackEvidence; counts?: Counts }
  | { kind: "committed-refresh-failed"; message: string }
  | { kind: "commit-unknown" }
  | { kind: "temp-not-removed"; after: "cancelled" | "failed" }
  | { kind: "abandoned" };
type RollbackEvidence =
  | "nothing-run" | "rolled-back" | "not-committed-closed" | "cleanup-unconfirmed" | "n/a";
```

- Phase is authoritative and set synchronously by the runner; progress frames never change the phase.
- Backup: one structure and one data step per table (empty and generated-only tables count), plus types and post-data steps.
- Restore: `processed = completed + skipped + unknown`, `stepsTotal = statements`; after the last statement the phase is `committing`/`refreshing` until the outcome is set.
- Coalescing via an injected scheduler; the terminal transition flushes and drops frames from another `jobId`.

## Close / Quit Guard (answers R2-4)

Atomic admission between starting a job and closing (answers R3-3), with no waiting:

- `admitClose(scope, intent?): { ok: true, lease } | { ok: false, message }` — one synchronous store transition: refused with the D8 message when the active job's origin is in scope (tab → its `tabId`/runtime; window → its `windowId`; app → any active job); otherwise a **lease** `{ leaseId, scope }` is added to `closing`. `closing` is a multiset of leases, not a set of scopes: independent closes of the same scope each hold their own lease, and `release(leaseId)` removes only that lease (idempotent).
- **Close intent**: the outermost entry point creates an intent token and passes it down (bridge → `closeTab`, quit guard → persistence → quit). `admitClose(scope, intent)` with a token that already holds a lease covering `scope` returns that lease without adding another, so a nested call neither double-admits nor releases its caller's lease. A call without a token (an independent shortcut, a second quit request) gets its own lease.
- While any lease covers a scope, `start` for an origin in that scope is refused (job identity check above), so no job can register between a passed close check and the final removal/quit.
- The lease is held until the close has actually finished or been abandoned: tab removal and disconnect done, or save/discard + persistence + quit done. Fire-and-forget entry points (`void quitApp()` in `useConnectionQuitGuard.ts:29–43`) are changed to own the lease inside the async function and release it in its `finally`, not in the event handler.
- Every close path calls `admitClose` **first**, before any unsaved-change prompt, discard/save mutation or tab removal: `requestCloseConnectionTab` (before the bridge call), its fallback path, `useConnectionActions.closeTab` (shortcuts and the bridged call; a nested admission of a scope already admitted by the same close returns ok and a no-op release), window close, and `useConnectionQuitGuard` (before its discard/save branches).
- `release(leaseId)` runs in the `finally` of the async close that owns the lease: when the close is declined, fails, or a save fails, that lease leaves `closing` and the tab/runtime/edits are untouched; other leases on the same scope remain. A completed close also releases.
- Pending dialog continuations that mutate before closing (`useConnectionActions.ts:985–991`, `connectionTabClose.ts:96–108`) call `admitClose` again before their discard/save step; a refusal there keeps the edits and shows the D8 message.
- A blocked close changes nothing. No coordinator, no waiting, no re-entrancy.
