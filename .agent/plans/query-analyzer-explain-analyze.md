## Task

- ID: query-analyzer-explain-analyze
- Requested 2026-10-22 (Query Analyzer review, batch 1 item 1): the Pro analyzer never shows a measured plan through the product; the Explain button always runs `EXPLAIN (FORMAT JSON)`.
- Already on `feat/query-analyzer-polish` (no new execution): own time/cost per node, explain input checks on a PostgreSQL lexer (`src/lib/sql/pgLexer.ts`), the analyzer opening for user-typed `EXPLAIN … FORMAT JSON` results (which go through the normal Run path and its safeguards).

## Decisions (human to confirm)

- **D1 Engines / versions:** PostgreSQL only, enforced by the backend. Supported and tested: 12–17 where containers are available; others recorded as untested.
- **D2 Statements:** read-shaped statements only (SELECT, WITH [RECURSIVE] … SELECT, VALUES, TABLE). Local writes to permanent tables are blocked by the server's read-only transaction; effects of functions/extensions outside that boundary (remote commits, locks, load) are an accepted remaining risk, disclosed in the confirmation. DML is out of scope.
- **D3 Safety modes:** allowed in normal, safe, production and lock modes (it cannot write locally), following Run's read rules: Touch ID in safe/production; profile lock keeps precedence (a profile-locked tab allows reads, as Run does). If a strict "no side effects at all" promise is required, this design cannot provide it and the action must be disabled in production/lock instead.
- **D4 Pro:** Pro-only action, checked before confirmation and immediately before dispatch; no automatic execution after an upgrade — the user clicks again. Estimated Explain stays free.
- **D5 Options and limits:** `EXPLAIN (ANALYZE, BUFFERS, FORMAT JSON)`, TIMING on (overhead disclosed). Phases and limits: connection setup (connect + BEGIN + settings + prepare) 10 s; statement 60 s (server `statement_timeout` plus a 62 s client bound); lock wait 5 s; cleanup (ROLLBACK + close) 5 s; whole operation hard cap 80 s. Setup and cleanup are outside the 60 s statement limit. Cancel requests server cancellation and closes the connection; effects already performed outside the transaction cannot be undone.
- **D6 History / privacy:** the **original** statement is added, with an optional kind tag "Explain Analyze", to the query history of the **profile tab** the action started from (the key `QueryHistory` reads: `queryHistory[activeProfileId]`, snapshotted before any async step), and only when a live attempt adopts the returned op id. If the attempt was cancelled/closed before the id came back, or the start call never answered, nothing is recorded even though the statement may have started; this is disclosed in the confirmation help. Refusals add nothing. Retention is the existing store's (in-app; no new persistence). Plans live only in the result tab. Existing explicit actions (copy JSON, export with its consent dialog, attaching to the AI chat by hand) can move a plan; nothing is sent automatically; no new telemetry. **Errors show only fixed, category-specific messages chosen from SQLSTATE/phase — no server-provided text** (primary message, DETAIL, HINT, notices) and no raw-text fallback, in the UI, logs or telemetry.
- **D7 Concurrency:** one Explain Analyze per runtime connection at a time (across its windows), using one extra disposable connection (no shared-pool slot); a second request is refused with a message. Multiple runtimes of the same profile may each run one.

## Goal And Visible Result

- **Explain Analyze** next to Explain in the SQL editor toolbar, and **Run with ANALYZE** in the analyzer's estimated-plan strip (re-measures exactly the statement and connection that produced that plan; refused if the connection changed).
- Confirmation (always; Cancel is the default button), wording proposed by Codex round 2:
  > Explain Analyze executes this statement in a local PostgreSQL read-only transaction. Local writes to permanent tables are blocked. We roll back when it finishes and close the connection used. Functions and extensions can still cause effects outside the transaction, including writes committed on remote servers, and can take locks. The statement may add database load or wait for locks. Time limit: 60 seconds; lock-wait limit: 5 seconds. Cancel asks the server to stop; it cannot undo effects already performed.
  plus database label and the statement's first line.
- The run appears as "Explain Analyze N" with the usual Cancel; the result opens in the analyzer as a measured plan.

## PostgreSQL semantics relied on (12–17)

- A read-only transaction rejects INSERT/UPDATE/DELETE (and MERGE from 15) on non-temporary tables, the documented DDL/administrative commands, and `nextval`/`setval` on permanent sequences — including inside functions and under EXPLAIN ANALYZE (SQLSTATE 25006).
- It does not sandbox: C/extension code, remote sessions (dblink, FDW), advisory locks, row locks taken by functions, load. Existing temporary-table DML is allowed (irrelevant here: the session is fresh, see below). Hot standby is stricter.
- `SECURITY DEFINER` changes privileges, not the access mode.

## Proposed Design

### 1. Classification (frontend, fail closed)

`classifyForAnalyze(sql)` (`src/lib/sql/analyzeClassify.ts`) on `pgLexer`:
- exactly one executable statement; unterminated input refused;
- leading keyword in {SELECT, WITH, VALUES, TABLE};
- refused if any word token (outside strings, comments, quoted identifiers) is one of: INSERT, UPDATE, DELETE, MERGE, INTO, COPY, CALL, DO, EXECUTE, PREPARE, DEALLOCATE, LOCK, NOTIFY, LISTEN, UNLISTEN, SET, RESET, DISCARD, VACUUM, ANALYZE, CLUSTER, REINDEX, REFRESH, CREATE, ALTER, DROP, TRUNCATE, GRANT, REVOKE, COMMENT, SECURITY, BEGIN, START, COMMIT, END, ROLLBACK, SAVEPOINT, RELEASE, ABORT, EXPLAIN;
- refused for row-lock clauses (`FOR UPDATE`, `FOR NO KEY UPDATE`, `FOR SHARE`, `FOR KEY SHARE`);
- positional parameters (`$1`) refused;
- the frontend lexer assumes `standard_conforming_strings = on`, and the backend **sets it** (`SET LOCAL standard_conforming_strings = on`) before preparing, failing closed if that fails, so the server parses the same string the lexer checked;
- known conservative false refusals (a column literally named `update` must be double-quoted; any of the listed words used as an unquoted identifier) are documented in the refusal message.
- Function calls are not filtered (cannot be done reliably); the read-only transaction is the boundary.
- The **exact** classified text (trailing comments/semicolons trimmed by `pgStatements`) is what the backend receives and wraps.

### 2. Backend operation (Rust), on the existing operation dispatcher

- New `OperationKind::ExplainAnalyze` with input `{ sql }`, dispatched by the existing `dispatch_operation` (returns the operation id; registers task, cancel-requested map, running-op cancel handle, `op:chunk_table`/`op:done`/`op:error` events). Only `EngineConnection::Postgres` implements it; other engines return `UNSUPPORTED` before spawning. It never uses the SQL busy registry or busy-retry.
- Rust re-checks the statement with a port of the same allowlist using shared fixtures (`src-tauri/tests/fixtures/analyze_classify.json`, read by both test suites). Backend refusal wins.
- **D7 permit:** acquired atomically in the dispatcher before spawning (per runtime connection id, in `AppState`), then moved into an `AnalyzeOwnership` value that the spawned future captures **by value**. Dropping the future — completion, error, or `task.abort()` even before its first poll — drops the ownership, which releases the permit and closes the connection if one exists. Spawn or registration failure releases it on the spot. The task handle is registered before the task can finish (spawn under the same lock as registration, or register first then spawn), so no stale task entry remains.
- **Isolated session:** a fresh connection from the runtime pool's manager (`pool.manager().create()`, via a direct optional `deadpool = "0.12"` dependency enabled by `engine-postgres` and `deadpool::managed::Manager as _`), same config/SSH endpoint/application name; no pool slot used. Editor session state (temp tables, SET values) is not present; such SQL fails here (documented).
- **Phases** (each under `tokio::time::timeout`, all under the 80 s cap; `cancel_requested` checked between phases):
  1. setup (10 s): connect; `BEGIN`; `SET TRANSACTION READ ONLY`; `SET LOCAL standard_conforming_strings = on`; `SET LOCAL statement_timeout = 60000`; `SET LOCAL lock_timeout = 5000`; prepare `EXPLAIN (ANALYZE, BUFFERS, FORMAT JSON) <stmt>`. The connection's cancel token is registered as soon as it exists; a cancel requested earlier fires immediately.
  2. query (62 s client bound): execute; decode the single row into a buffer — **not emitted yet**.
  3. cleanup (5 s): `ROLLBACK`; only after its acknowledgement is the buffered plan emitted as one chunk followed by `op:done`. Rollback failure, timeout or disconnection → `op:error`, never a measured result.
  4. close: always drop the connection (its connection task is aborted; the server ends the session). Local cleanup is bounded; server-side termination is observed in tests for cooperative cases, not promised for native code.
- Errors: `op:error` carries only a fixed category (`refused`, `read_only_violation` 25006, `timeout` 57014 not requested by the app, `lock_timeout` 55P03, `permission_denied` 42501, `object_missing` 42P01/42703/42883, `syntax_error` 42601, `connect_failed`, `setup_failed`, `rollback_failed`, `failed`). The frontend maps each to a fixed sentence. No server text of any kind (primary message, DETAIL, HINT, notices, `format_pg_error`) is forwarded, logged or tracked; non-database errors (I/O, decode, timeout) map to categories too. App-requested cancel ends as cancelled through the existing classification.
- No logging of SQL, plan or identifiers.

### 3. Frontend entry point

`useSqlRunner.startExplainAnalyze({ windowId, sql, origin })` — the only caller for both buttons:
1. Reserve the per-window in-flight guard immediately; released on every terminal path.
2. Snapshot: runtime connection id + generation, profile id, engine, `sqlSafetyMode`, `isProfileLocked`, window id, classified statement. For "Run with ANALYZE", `origin` carries the source run's statement and connection; refused if the connection differs.
3. Pro (`requirePro`), engine, classification. Refusals → an error run with the reason; nothing executed, no history.
4. Read policy via a helper extracted from `startRun` (`readRunPolicy(mode, locked)` → `{ requireTouchId }`), so Run and this action share one implementation; `startRun` behaviour unchanged and covered by existing tests.
5. Touch ID when required; then the native confirmation.
6. Immediately before dispatch, re-read **current** state and abort on any change: connection id/generation, profile, engine, safety mode, profile lock, Pro, window open, statement. No dispatch after a cancel/close/reset in the meantime.
7. **Attempt lifecycle:** each attempt gets an `AnalyzeAttempt { id, epoch, abort, profileTabId }` in a module-level registry keyed by window id (outside the run, so it survives run/window removal). The per-window guard is owned by the attempt id; a finalizer releases it only if the registry still holds that same attempt. Close run, reset, window clear/recreation, Cancel and unmount abort the attempt, bump the epoch and release frontend ownership immediately — even when IPC never settles.
8. **Attempt-wide deadline:** a 100 s frontend deadline starts before `operationBus.ensureInit()`. Initialization and the start call each race against abort and that deadline; on abort/deadline the attempt ends at once (error "No response" or cancelled) and a **detached late-id continuation** stays attached to the pending start promise: if an op id ever arrives, it calls `operationCancel(opId)` and publishes nothing. After `ensureInit()` resolves, signal/epoch/current policy (step 6) are re-checked again immediately before IPC. The dedicated wrapper (`src/lib/tauri/explainAnalyze.ts`) never retries and never uses busy-retry.
9. History entry (D6) only when the live attempt adopts the op id, under the snapshotted profile-tab key; never written to a recreated or reassigned tab.
10. The run slot uses the stream lifecycle with an **opt-in "terminal-only" mode** for this op (`useSqlStreamResult` registration flag): no 1.2 s idle-done, no 65 s unsubscribe; it stays running with Cancel available until `op:done`/`op:error`/cancel, with a watchdog at 80 s + 15 s that reports "No response from the server" (error, never a successful empty result). Ordinary streams keep their current behaviour.
11. The single-row result is parsed by `planFromResult` (no fallback) and shown in the analyzer.

## Plan Review — round 1 (Revision 1)

Reviewed by Codex, 2026-10-22. **Recommendation: revise before approval.** This is an execution feature, not an extension of estimated EXPLAIN. The current design leaves safety-critical enforcement and transaction ownership unspecified. Findings below concern the proposed plan; existing-code gaps are identified as evidence, not claims that this unimplemented feature is already vulnerable.

### Findings

1. **[P1] Statement checks / D2: `isMutatingStatement` cannot classify safe execution.** `src/lib/sql/detect.ts` checks only the first keyword after non-nested comment skipping. Both `WITH changed AS (DELETE FROM t RETURNING *) SELECT * FROM changed` and `WITH x AS (SELECT 1) UPDATE t SET ...` return false. So do `SELECT write_function()`, `SELECT nextval(...)`, and locking SELECTs. `EXECUTE` can conceal prepared DML. Treating false as “read-only” either bypasses the intended mode policy or causes unexpected server failures when read-only is finally enforced. Use a PostgreSQL-aware, fail-closed classification contract: permitted read-shaped statement, permitted write-shaped statement, or unsupported/unknown. Inspect all CTE bodies and the terminal statement; distinguish `SELECT INTO` and every row-lock clause (`FOR UPDATE`, `NO KEY UPDATE`, `SHARE`, `KEY SHARE`). Reject unknown syntax, nested EXPLAIN, prepared EXECUTE, DO/CALL, COPY in both directions, transaction/session control, DDL and maintenance explicitly. EXPLAIN support is broader than the product's chosen allowlist (including EXECUTE and CREATE TABLE AS); “unsupported by this action” is the accurate refusal reason. Do not attempt to prove arbitrary functions harmless using their names or volatility labels. SELECT-only is a narrower launch scope, not a side-effect guarantee.

2. **[P1] Execution / read-only enforcement: make the backend own an atomic analyze contract.** Frontend checks alone and independent optional `rollback` / `read_only` booleans permit contradictory payloads and accidental fallback to ordinary committing execution. Prefer an explicit PostgreSQL analyze execution mode with the backend building the wrapper, enforcing one supported original statement, forcing rollback, and requiring server read-only for the restricted mode. Alternatively specify equally strong validation for the proposed flag. Reject incompatible `validate_only`, non-PostgreSQL requests and raw non-transactional execution before dispatch; reject rather than ignore unsupported options. In `postgres/operation.rs:132-175`, CREATE/ALTER/DROP DATABASE bypass the transaction entirely, so a generic rollback flag must be rejected before that branch. Never submit `BEGIN`, EXPLAIN and `ROLLBACK` as three operations: pool checkout can differ. In lock/production mode a classified write must be blocked before dispatch, and any permitted request must also use server read-only. PostgreSQL read-only rejects ordinary table writes even through EXPLAIN ANALYZE, but is not a sandbox for external functions, temporary objects or session effects. State that boundary explicitly. See [transaction access modes](https://www.postgresql.org/docs/18/sql-set-transaction.html).

3. **[P1] Files / transport: the actual stream path drops the required safeguards.** `useSqlRunner.ts:299` forwards only SQL/window/connection. `useSqlHistoryRunner.ts` similarly accepts no execution options and routes EXPLAIN to `startSqlQueryStream`. `query.ts:478-489` sends only SQL, batch size, max rows and client mode, although the direct helper forwards server timeouts and read-only. Adding a builder and Rust flag will therefore not wire the feature safely. Expand the plan's file list and typed execution contract across toolbar/analyzer → runner → history runner → direct/stream wrapper → IPC types → PostgreSQL runner. Verify identical rollback, read-only and timeout semantics in both modes. Default ordinary queries and estimated Explain must keep their existing behavior. Add payload-level tests proving every safeguard reaches Rust, not just builder tests.

4. **[P1] Rollback / cancellation / pooling: replacing the final COMMIT is insufficient.** `postgres/operation.rs` has separate validation and execution commits and many early returns that drop the transaction; normal chunks can be emitted before transaction finalization. `operations/dispatcher.rs:11-44` sends cancellation, aborts the task, and releases the stream busy slot immediately. The plan must cover errors during setup/prepare/query/decoding/stream emission, timeout, task abort, cancel during finalization, and rollback failure. Await rollback on ordinary success/error paths; emit successful completion only after rollback acknowledgement. Use cancellation-safe ownership so interrupted or uncertain cleanup discards/closes the physical client instead of returning it to the pool. The existing `postgres/session_signal.rs::DiscardGuard` is a relevant local pattern, not a reason to assume the query runner already has this guarantee. Test the next operation on the same pool after each failure. Because session-level effects can survive even a successful rollback, use an isolated disposable session for arbitrary analyzed functions, or define and test a complete reset policy; rollback alone is not a safe pool reset. Do not automatically retry a statement that may already have executed.

5. **[P1] Safety parity / confirmation / Pro gating: define one execution entry point and bind consent to its input.** `startRun` currently validates original statements, applies profile-lock precedence over safety mode, blocks mutation in production/lock, and authenticates safe/production; `startExplain` omits all of that. Extract/reuse the policy without treating the existing regex as a security guarantee. Both toolbar and estimated-plan-strip actions must call the same gate on the original SQL, never on the EXPLAIN prefix. Snapshot statement, connection/profile, engine and policy before confirmation; revalidate connection, lock/mode, entitlement and cancellation after asynchronous upgrade/Touch ID/dialog steps. Abort on changed context rather than executing different SQL or a stale target. Require explicit confirmation for every execution; cancel/failed authentication/upgrade dismissal must produce zero execution and no history entry. Keep Cancel as the default/safe choice. Include target profile context, statement kind, actual effective timeout, locking/load risk, and rollback limitations. Pro must be checked in the execution handler, not only by hiding the button or relying on `SqlResultsPane.tsx:413` (which currently gates rendering only). Preserve free estimated Explain. Do not silently rerun after purchase or fall back to ordinary Run on failure.

6. **[P2] Confirmation / Risks: the rollback limitations are partly incorrect and omit SELECT risks.** Transactional PostgreSQL `NOTIFY`/`pg_notify` is delivered only on commit, so a notification made in this transaction is discarded on rollback; a remote independently committed notification is different. Sequence `nextval`/`setval` changes survive rollback in write transactions. Session advisory locks survive rollback; transaction advisory locks do not. External calls, remote commits and session state may also escape local rollback, including through SELECT functions or DML triggers. Warn for every analyzed statement, not only those classified as DML; never promise “no changes” or that cancellation reverses external work. Correct the claim that advisory locks generally release on rollback. Explain that table changes are rolled back only after successful cleanup. Sources: [NOTIFY](https://www.postgresql.org/docs/18/sql-notify.html), [sequences](https://www.postgresql.org/docs/18/functions-sequence.html), [advisory lock scope](https://www.postgresql.org/docs/18/explicit-locking.html#ADVISORY-LOCKS).

7. **[P2] Timeouts / Cancel: existing UI cancellation is not an end-to-end guarantee.** `cancelRunOperations` only cancels stream slots with a known op ID. Cancellation before `onRunSql` resolves can leave a late-created operation untracked; direct slots have no cancellable handle. The stream helper has no execution deadline and does not forward server timeout options. `runStatements` unsubscribes after 65 seconds regardless of actual completion. Specify an AbortSignal/operation lifecycle covering confirmation through late operation creation, close/reset/unmount and direct/stream modes; cancel late op IDs even when the run generation changed. Define a bounded statement timeout plus short lock timeout and a separate pool-acquisition/cleanup deadline. The current PostgreSQL default is 60,000 ms, clamped to 100–300,000 ms; the plan identifies no actual editor setting to inherit. Resolve that explicitly and show the effective limit. Cancellation must never produce a measured-success result from an empty/partial response. Clearing UI state or releasing the busy slot is not proof that database work stopped.

8. **[P2] Single-statement validation: the editor splitter is not a PostgreSQL security parser.** `splitSqlStatements.ts` does not nest block comments, accepts unterminated quotes/comments, treats backslash as an escape in all quoted strings/identifiers, and accepts dollar tags without PostgreSQL's full lexical rules. PostgreSQL ordinary strings under `standard_conforming_strings` differ from E-strings. Comment-only tails can count as statements. Keep the splitter for editor selection if useful, but validate with PostgreSQL-correct rules and reject uncertainty before consent. Backend prepared-statement parsing already rejects multiple commands on the transactional path; preserve that defense and never substitute `batch_execute` for user SQL. Tests must include nested comments, leading/trailing comments, comment-only input, semicolons inside strings, E-strings versus ordinary strings, quoted identifiers, dollar quotes and malformed input. Verify the exact validated statement is the one wrapped and executed, with no trailing statement or wrapper-breaking normalization.

9. **[P2] Verification: replace broad assurances with failure-oriented acceptance tests.** Existing `explain.test.ts` checks estimated wrappers and `splitSqlStatements.test.ts` covers basic lexical cases; the proposed test list does not demonstrate the safety contract. Require: CTE DML and terminal DML; function writes/external calls; sequences in write mode versus rejection in read-only; all locking SELECT variants; DO/CALL/COPY/EXECUTE/transaction/DDL rejection; both entry points; normal/safe/production/lock × profile lock × Pro matrix; Touch ID rejection and dialog cancellation; context changes and duplicate clicks; zero execution on denied paths; actual serialized options in both transports. Disposable PostgreSQL integration tests must prove rollback after successful INSERT/UPDATE/DELETE and supported-version MERGE, trigger effects, failures after some effects, timeout, cancellation before op ID/while waiting for locks/after rows arrive, and safe connection reuse or disposal. Use a second session to verify no committed rows, no held locks and no delivered transactional NOTIFY. Exercise rollback failure/disconnection and unsupported-engine rejection. No tests may run against a user database. A successful SQL string assertion is not evidence of rollback.

10. **[P2] Privacy / D6: cover plan data, histories and error paths, not just SQL text.** `useSqlHistoryRunner` records submitted SQL locally; decide and document whether analyze executions enter existing local history and ensure any rerun retains the same safety gates. Plans may contain literals, relation/index names, predicates and trigger/function identifiers. Do not add plan bodies, original/wrapped SQL or raw driver errors to telemetry/logs/crash breadcrumbs, or automatically forward plans to AI. Current `analytics.ts::sanitizeProp` categorizes error strings; preserve and test that behavior through both query helpers. Keep analytics opt-in and test emitted properties, including failed analysis. Normal local display/history is distinct from external transmission; make any new retention/export behavior explicit.

11. **[P3] Measurement wording / D5: measured execution is not normal end-to-end latency.** Keep “Measured plan,” but document instrumentation overhead and the rollback context. Execution time excludes client result transfer; deferred constraint triggers are not measured and rollback does not run their commit-time work. Never label this a successful committed write or total user-query duration. `TIMING ON` is reasonable for per-node time views, with its overhead disclosed; `TIMING OFF` would require adapting those views. See [EXPLAIN caveats and trigger timing](https://www.postgresql.org/docs/18/using-explain.html).

### Opinions on D1–D6

- **D1 — Agree: PostgreSQL only.** Enforce this in backend dispatch as well as UI. Avoid unsupported claims about other engines' transaction semantics; they need separate designs and tests.
- **D2 — Recommend restricted read-shaped statements for the first release, with mandatory server read-only and forced rollback.** Reject locking SELECT, SELECT INTO, unknown forms and prepared EXECUTE; allow WITH only when classification covers the entire statement. This still requires universal side-effect warnings and session isolation. Add DML only after the explicit rollback/disposal contract and failure matrix above are implemented and verified. If DML ships initially, limit to INSERT/UPDATE/DELETE and supported-version MERGE including fully classified CTEs; do not describe regex classification as sufficient.
- **D3 — Agree conditionally with the proposed mode matrix.** Production/profile lock/lock mode block classified writes; safe mode may allow explicitly approved DML after Touch ID and confirmation once D2's protections exist. Safe/production reads still authenticate as today; lock precedence remains unchanged. Server read-only protects restricted runs, while the product must disclose its side-effect boundary. Do not broaden this task into silently changing ordinary Run semantics.
- **D4 — Agree: Pro-only action.** Central handler gate before execution, with another eligibility check after asynchronous prompts; free estimated Explain remains available. Entitlement loss must not bypass cleanup of an already running operation.
- **D5 — Agree: BUFFERS and TIMING ON initially.** Keep JSON format and planning/execution fields; disclose instrumentation overhead. Defer SETTINGS/WAL as proposed. Limits apply to executing the underlying statement, not the one returned plan row.
- **D6 — Agree conditionally: existing opt-in, sanitized run analytics only.** No new raw SQL, plan/error content or sensitive identifiers. Add payload assertions and resolve local-history behavior explicitly.

### Remaining findings

1. **[P1] Consent can outlive its safety policy.** Frontend step 5 checks connection/profile/statement/Pro/window, but not the snapshotted safety mode, profile-lock state, cancellation or runtime connection generation. A switch from normal to safe/production during confirmation could execute without required authentication. Re-read authoritative current state after asynchronous gates and immediately before dispatch; abort on any relevant context change, including close/reset/unmount. Reserve the in-flight guard before upgrade/auth/dialog and release it in every terminal path. Do not auto-dispatch after purchase or route failure to ordinary Run. Bind analyzer-strip SQL to the original statement and target that produced its plan, rather than silently using edited SQL or another connection. Define how the existing Run read policy is reused without copying a second policy implementation; list the shared helper/tests if extraction is necessary. Keep ordinary Run and estimated Explain behavior unchanged.

2. **[P1] Operation ID needs a concrete two-stage lifecycle and safe cleanup ordering.** A normal awaited Tauri command returns once; `query_explain_analyze { runtime_connection_id, sql } -> plan` cannot also return its ID before execution. Choose an explicit protocol: for example, a frontend-created unique ID included in start/cancel with backend registration before pool acquisition and a result channel, or a start command returning an ID followed by terminal events. Specify ownership by connection/window/run generation, duplicate-ID rejection, bounded cancellation tombstones, listener registration before start, and cleanup of registry/task entries. Existing `cancelRunOperations` only handles stream slots; a dedicated-command run will not become cancellable merely by adding an ID. Update Cancel, clear/reset, close/unmount and late-result handling explicitly and list affected files.

Cancellation must latch even before checkout/token registration; a one-shot PostgreSQL cancel request between prepare and query can otherwise cancel nothing and let query execution begin. Check cancellation between phases, stop dispatch after cancellation, and discard even when cancellation fails. Prefer the driver's PostgreSQL cancel token protocol; do not conflate that with SQL `pg_cancel_backend(pid)`, which requires a separate connection/permissions and must not queue behind the held pool slot. Define timeout (57014) versus user-cancel classification using operation state; lock timeout (55P03) needs a deliberate result mapping. Never publish a measured success from a cancelled/stale operation.

Await ROLLBACK on ordinary success/error paths, publish success only after acknowledgement, and bound rollback/cancel cleanup. On task abort, timeout or rollback failure, close/discard and report failure/cancelled rather than claiming rollback succeeded. The guard must never be disarmed or leave ownership in a detached task. `Object::take` removes pool reuse; prove the detached driver's physical session actually closes and locks disappear, rather than assuming a Rust drop instantly stops server work. Retain busy/cleanup ownership until terminal cleanup; never retry an analysis that may have executed. Start the 5 s acquisition deadline explicitly, define whether the 70 s absolute deadline includes checkout, and include setup/prepare/cleanup within bounded lifetimes.

3. **[P1] Confirmation still promises more than read-only plus rollback provides.** “So table data cannot change” includes independently committed remote writes and temporary data; “Cancel stops it” promises immediate termination and reversal of effects that may already have happened. These claims are especially misleading when permitting this action in production/lock modes. Proposed replacement for human approval:

> Explain Analyze executes this statement in a local PostgreSQL read-only transaction. Local writes to permanent tables are blocked. We roll back on completion and discard the connection; if cleanup fails, we close it. Functions and extensions can still cause external effects, including independently committed remote writes, and can acquire locks. The statement may add database load or wait for locks. Statement time limit: 60 seconds; lock-wait limit: 5 seconds. Cancel requests cancellation; it cannot undo external effects already performed.

Include target profile/database and statement kind; keep Cancel the default. Clarify separate checkout/cleanup time outside the statement limit. Do not recommend manually typing EXPLAIN ANALYZE as an equivalent safe fallback: ordinary Run commits and its first-keyword mutation checks do not provide this dedicated action's protections. If retaining that guidance, explicitly disclose the changed execution contract and require a fresh normal-Run decision.

4. **[P2] Specify PostgreSQL 12–17 semantics accurately; fix the sequence test.** Across these versions, local read-only prohibits DML on non-temporary relations and the documented DDL/administrative commands, including execution through EXPLAIN ANALYZE. MERGE joins that list from PostgreSQL 15. SQL/PLpgSQL functions attempting ordinary permanent-table writes are subject to the same restriction; SECURITY DEFINER changes privileges, not transaction access mode. This is not a sandbox for privileged native code, extensions or remote sessions. Existing temporary-table DML is permitted on a primary; creating temporary tables in this transaction is prohibited. Hot standby imposes stronger restrictions, including temporary-object writes. See official [12](https://www.postgresql.org/docs/12/sql-set-transaction.html), [13](https://www.postgresql.org/docs/13/sql-set-transaction.html), [14](https://www.postgresql.org/docs/14/sql-set-transaction.html), [15](https://www.postgresql.org/docs/15/sql-set-transaction.html), [16](https://www.postgresql.org/docs/16/sql-set-transaction.html), and [17 access-mode documentation](https://www.postgresql.org/docs/17/sql-set-transaction.html).

`nextval` and `setval` on permanent sequences fail with 25006 in this mode. Replace “nextval side effect survives” with rejection plus unchanged sequence value checked from another session. Existing session-local temporary sequences are an exception; remote sequence changes are outside this transaction. Sequence changes survive rollback when execution is permitted, such as ordinary read/write mode. PostgreSQL's [12 implementation](https://raw.githubusercontent.com/postgres/postgres/REL_12_STABLE/src/backend/commands/sequence.c) and [17 implementation](https://raw.githubusercontent.com/postgres/postgres/REL_17_STABLE/src/backend/commands/sequence.c) explicitly apply the read-only check to both functions except local temporary sequences.

Read-only does not mean lock-free: normal SELECT takes relation locks; advisory-lock functions remain callable. Transaction advisory locks release on transaction end; session advisory locks survive rollback until explicit unlock/session termination. A function can take allowed explicit table locks without exposing a LOCK token in the caller. Local transactional `pg_notify` notifications are suppressed by rollback, unlike remote independently committed notifications. Functions can sleep, change session settings subject to PostgreSQL rules, invoke privileged effects, or contact external services. See [locking](https://www.postgresql.org/docs/17/explicit-locking.html), [NOTIFY](https://www.postgresql.org/docs/17/sql-notify.html), and [dblink](https://www.postgresql.org/docs/17/contrib-dblink-function.html). Remote connections do not inherit local read-only, rollback, lock_timeout or guaranteed cancellation. Do not describe every FDW as equivalent to dblink; extension-specific behavior needs separate evidence.

5. **[P2] Define the token filter's supported forms and lexical contract.** It conservatively rejects tokenized DML anywhere, including modifying CTEs and terminal DML after WITH; server read-only is the additional enforcement boundary. `WITH RECURSIVE` SELECT, nested read CTEs, TABLE, VALUES, and set-returning functions should have explicit fixtures. Recursive and set-returning queries can consume substantial resources; functions inside VALUES, CTEs, views, FROM/LATERAL and expressions retain the same side-effect boundary as SELECT functions. Denying named functions is not a reliable general fix: wrappers, quoted names, operators and views can hide them.

Match all four clauses as significant token sequences: `FOR UPDATE`, `FOR NO KEY UPDATE`, `FOR SHARE`, `FOR KEY SHARE`, with comments/newlines, nested queries, `OF`, `NOWAIT` and `SKIP LOCKED`. Current shorthand is ambiguous. UPDATE token rejection covers two forms, but SHARE forms need their own check. Functions that acquire locks contain none of these tokens. Keyword bans may reject legal unquoted names/aliases (for example an unreserved keyword used as a column name); document conservative refusal rather than claiming full grammar support. A leading-keyword/token filter also rejects some parenthesized queries and cannot prove arbitrary WITH syntax valid; backend parse errors must remain structured failures with no fallback.

`pgLexer.ts` assumes ordinary strings use `standard_conforming_strings=on`; a runtime session can differ. Pin a compatible lexical setting before user SQL is prepared, or reject unsupported settings and test that choice. Port UTF-8/token boundaries deliberately rather than assuming JavaScript string offsets equal Rust byte offsets. Validate the full original input, reject positional parameters without bindings, preserve a single statement's bytes except explicitly specified terminal-semicolon/comment removal, and prepare the final wrapper through the extended protocol. Never split and silently execute only the first statement. Share fixtures for nested comments, E/ordinary/dollar strings, quoted/Unicode identifiers, malformed input and comments hiding keywords. Prepared parsing is an extra defense, not evidence that frontend and backend classifiers agree.

6. **[P2] Always-discard is justified, but has cost and session-compatibility consequences.** Each analysis consumes a pool slot and then removes a reusable physical connection. Replacement can require authentication, TLS/SSH/network setup; repeated analyses across windows can cause churn, server connection pressure and starvation of normal Run. A pooled checkout can also inherit existing session state before analysis, and arbitrary pooled sessions do not reliably represent the editor's temp objects, SET state or advisory locks. Specify baseline session initialization, compatibility with session-dependent SQL and failure behavior when session-affine client modes are active. Keep discard-always for this scope; do not substitute a partial reset for performance. Decide shared-pool versus isolated disposable capacity, concurrency per connection/profile across windows, checkout timeout and whether benchmark timing excludes connection setup. Verify ordinary operations continue after repeated success/cancel/failure. Show resource cost in engineering acceptance criteria; a new user-facing pool setting is unnecessary.

7. **[P2] Local history and privacy need concrete integration contracts.** D6 chooses local history, but the new path bypasses `useSqlHistoryRunner` and lists no history/state model changes. Specify when a persisted history entry is created, original SQL versus wrapped SQL, stored execution kind, and whether plans are retained. Distinguish an ephemeral refusal/error run from persisted execution history: denied Pro/auth/dialog/classification paths must not create an executed-history entry. Every retry/rerun from history must re-enter `startExplainAnalyze`, with fresh gates and confirmation, never generic Run. Clear/reset must cancel the operation before discarding its ownership.

“No new analytics” is useful but insufficient: trace existing invoke errors, driver notices, result logging, crash breadcrumbs and AI/export paths. Return fixed safe error categories; do not include raw SQL/plan/error DETAIL/HINT/CONTEXT or NOTICE content in external telemetry. Plans themselves contain sensitive literals/identifiers. Preserve opt-in and existing sanitization; add assertions for successful, refused, read-only violation, timeout and failed/cancelled runs. Normal local history/display differs from transmission; decide retention/export behavior explicitly rather than promising no SQL leaves the device while leaving optional integrations undefined.

8. **[P2] Complete release acceptance criteria before implementation.** Add tests proving the dedicated IPC path is used by both entry points and backend independently refuses unsupported engines/input. Run shared lexer fixtures in both languages. In disposable PostgreSQL 12–17, verify permanent-table function writes and permanent-sequence calls fail; both CTE DML forms and row-lock variants refuse; read WITH RECURSIVE/VALUES/TABLE/SRF cases work. Do not require successful DML rollback tests for a release that refuses DML.

Use a second session to observe unchanged rows/sequences, transactional NOTIFY suppression, advisory lock lifetime and eventual backend termination. Include pg_sleep timeout/cancel, lock waits, dblink remote commit (where extension is available), cancellation before ID/checkout/token and between prepare/query, cancellation after query but before rollback, close/reset/unmount, lost responses, rollback failure/disconnection, setup/prepare/decode errors, policy changes during every async gate, and repeat pool use. Extension-dependent tests may be explicitly conditional; absence is a stated limitation. Verify no success before rollback acknowledgement, no retry, no stale result publication, and bounded registry/connection cleanup. Add privacy/history rerun assertions and preserve bounded plan parsing. Declare the tested version matrix and any support limits; static documentation checks are not a substitute for live tests.

9. **[P3] Clarify measured-plan scope in the analyzer hint.** Execution time excludes result transfer and includes EXPLAIN instrumentation; it is not application end-to-end latency. It also excludes connection acquisition and deferred commit-time work. A rolled-back, disposable-session run can differ from ordinary Run because of cache, session state and transaction context. Preserve the existing measured/estimated distinction and bounded JSON ingestion; avoid interpreting successful analysis as a committed business operation.
