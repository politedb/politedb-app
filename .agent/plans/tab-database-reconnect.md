## Problem

A tab opened on another database ("Open database", `MenuBar.onOpenDatabase`) has `databaseOverride` (label `"<profile> · <db>"`) and gets its runtime connection from `connectionCreate(withDatabaseInput(profile.input, db))`.

Runtime connection ids are not persisted (`persistentStore.ts:135-144`). A tab without one reconnects by profile only, to the **profile's own database**:

- `useEnsureRuntimeConnection.ts:59` (auto restore) and `:117` (manual reload; `useConnectionActions` `refreshRuntimeConnection` at `:462` and patch apply at `:552` go through it);
- `useLoadTableData.ts:67`, and `:150-154` keeps a table's previous connection id over a new tab one;
- `useCreateSchemaTable.ts:40` (direct `profileConnect`);
- `ConnectionFormDialog.tsx:180-210` save-and-connect attaches the profile's default-target runtime to an existing (`reuseTabId`) tab, keeping its override;
- `runtimeConnection.ts:13-21` promotes any table-data connection under the tab to the tab's runtime; `connectProfileOnce` de-duplicates by profile id only;
- below the hooks, `sqlLoader.ts:213,454` de-duplicates size/FK work by schema/table/engine only, `sqlExecute.ts:63-73` keeps `curPrev.connectionId ?? connId`, and `cassandraLoader.ts:11-24` / `cassandraExecute.ts:21` fall back to the saved profile keyspace.

The tab then runs on the profile's database while its label, breadcrumb, SQL scope and drop checks say the override. Observed 2026-10-30 (human's report): after an app restart a tab "zeniuz · test" listed `zeniuz_dev`'s tables; a restore started there ran against `zeniuz_dev` and was cancelled before COMMIT. Pre-existing; not caused by the backup/restore branch.

## Goal

A tab always runs on the target it was opened on. Any path that gives a tab a connection connects to that target or fails visibly; nothing falls back. A runtime opened from settings that have since been saved differently, or on a different target than the tab's, cannot be used for the covered operations.

Out of scope, stated plainly: (1) the SQL session's **current** database after session-changing SQL typed by the user (`USE`, `SET search_path`, …) — D1 shows and D3 checks the **startup** target; (2) atomic profile save with Keychain secrets and response ordering of profile saves in the frontend — separate follow-up plan.

## Definitions

- **Explicit override**: a tab's `target.database` when `target.kind = "override"` (R12), trimmed, non-empty, on an engine with Open database support (PostgreSQL, MySQL, MariaDB, SQL Server, MongoDB, SQLite path, Oracle service, ClickHouse, Cassandra keyspace). An override on another engine is invalid (error, no connect).
- **Default target**: the saved profile's own target. A tab without an explicit override connects with **no override** (the backend uses the stored input); the frontend never sends a fallback/display value as an override. Snowflake, D1, Turso, Sheets, DuckDB, Redis keep connecting as today.
- **Profile revision**: a backend-issued random UUID v4 on every saved profile, assigned by the profile store on every create, update and import replacement (`profile_create_with_id`, `profile_update`, `profile_upsert_many`, reached by `commands/profile/import.rs:48` and `profiles/import_external.rs:78`); an imported value is never trusted. A profile without one gets one at load, persisted under R14 before it is returned. The backend keeps an in-memory `profile_id → current revision` map, updated in the same R14 critical section as every write and on load; a removed profile has no entry. `updated_at` is not used. Revisions are compared for equality only. The frontend receives `revision`; a frontend revision comparison **never authorizes** backend execution, runtime reuse or draft migration (R20 is the freshness authority); it may only conservatively invalidate generations/caches under R16.
- **Runtime target identity** (backend-recorded, transient): `{ profileId | null, profileRevision | null, override: string | null, engine, display }`, captured from the exact stored profile snapshot used to connect (read under R14, lock released before network work), before the input is consumed and before SSH rewriting, published with the runtime by R13. `display` is a normalized, nonsecret label (database, keyspace, service, SQLite full path; SQL Server empty → `master`). Runtimes created without a profile (`connectionCreate` by other callers, connection test) have `profileId: null`; they are never adopted by a tab and are not subject to R20.
- **Stale runtime** (backend): a runtime whose `profileId` has no current revision (profile removed) or whose `profileRevision` differs from the current revision.
- **Match** (frontend): a runtime matches a tab iff its identity has the tab's `profileId` and the tab's override (null = default) **and** it is the tab's authoritative runtime (R4). Revision freshness is not judged in the frontend; it is enforced by R20.

- R6 Profile edits (form reuse and plain edits): Save uses `profileSave` (unchanged save path; secret handling unchanged, see Follow-ups). Saving changes the stored revision, so **every runtime of that profile becomes stale in the backend at once** (R20), whatever the frontend has published. The frontend: (a) on Save+Connect for a reused tab, refuses before saving if the tab has dirty state; after a successful save it performs a forced acquisition (never reuses an existing runtime) with the tab's override; on success it installs the new runtime (dirty check repeated), invalidates (R5) and removes the superseded runtime it owns; on failure the tab keeps its old runtime, which the backend now refuses, and shows the error with Reload; (b) Save-only and sibling tabs: nothing is reconnected; their next admitted operation is refused by R20 with `RUNTIME_STALE`, which the frontend maps to "The connection settings changed. Reconnect this tab." with Reload and a generation bump (R5). Dirty drafts stay. An engine change keeps an explicit override only when the new engine supports overrides; otherwise the tab becomes `unknown` (R7).
- R7 Unknown target recovery (D4): a tab whose target is `unknown` does not connect; it shows "This tab's database could not be determined. Close it and open the database again." Drafts are never migrated to another tab.
- R8 Missing or unopenable override target = connection error on the tab (existing error UI with Reload/close), never a fallback. Per engine:
  - PostgreSQL, MySQL/MariaDB, SQL Server, Oracle (service), ClickHouse, Cassandra: the driver's connect/USE fails; mapping tests; live only for PostgreSQL (others listed as unverified).
  - Cassandra: keyspace as a quoted identifier with embedded `"` doubled, replacing raw `USE {ks}` (`cassandra/driver.rs:160`).
  - SQLite: an override connect opens without `SQLITE_OPEN_CREATE` (internal `ConnectPolicy`, R13a): a missing file is an error and nothing is created. Profile-level opens and the template keep creating. `:memory:`, empty and `file:` URI paths are invalid overrides.
  - MongoDB (chosen limitation of this path): the selected database is set (auth database `admin`, TLS, SSH untouched) without an existence check; a dropped database shows as empty under its correct name; later reads/writes may fail authorization or recreate it.
- R9 Secrets: the override is applied in Rust to a clone of the stored profile input (keeping every `SecretRef`, SSH, TLS and option); the clone is never saved, re-keyed or sent to the frontend. Profile save secret handling is not changed by this plan.
- R10 Privacy: touched paths log bounded error categories only (no `format!("{e}")` under a code name), no database name, path, profile label or input; the existing raw-error/label traces at `connect.rs:250-255`, `lifecycle.rs:25,65` are reduced for these paths, including nested driver/tunnel traces reached by them. Telemetry: reconnect/stale events carry only an allow-listed set of fields (test asserts the exact keys; no `databaseOverride`/`resolvedDatabase`/path keys); opt-out preserved. Local connection history keeps its current user-facing behavior.
- R11 Persisted state: runtime ids, identities and owners stay transient; restored windows drop any persisted `connectionId` (`src/types.ts:68-72`).
- R12 Tab provenance (D4): every tab persists `target: { kind: "default" } | { kind: "override", database } | { kind: "unknown" }` (`src/stores/screen.ts`, `persistentStore.ts:42-51,135-144,298-334`), set when the tab is created (profile open → default; Open database → override; form/template → default unless reusing a tab, which keeps its own). Restore: a persisted `unknown` stays unknown; a record **without** `target` (every tab saved before this change, default ones included) becomes `unknown` — labels are never consulted; an `override` with a blank database, an override on an engine without override support, and a malformed `target` (unknown `kind`, wrong types, null) are `unknown`. When `target` and the `databaseOverride` mirror disagree, `target` wins; the mirror is rewritten from a valid `target`, never the reverse. Applies to inactive tabs.
- R13 Registry publication: identity is inserted into `runtime_targets` **before** the runtime is inserted into `connections`; a failed publication removes the identity it inserted; `connection_remove` removes the connection first, then the identity. `connection_list` builds each DTO while holding that connection's map guard and reads its identity inside it (no clone-then-lookup); publication and removal never hold the identity-map guard while waiting on the connection map. A list therefore never shows a connection without identity.
- R13a Connect policy: an internal, non-persisted `ConnectPolicy { sqlite_create: bool }`; `EngineDriver` gains `connect_with_policy(input, &ConnectPolicy)` with a default delegating to `connect`; only SQLite overrides it. An internal `create_runtime(input, policy, target)` is used by `connection_create` (default policy, no profile), `profile_connect` and `profile_save_and_connect` (target from the stored profile).
- R14 Profile store serialization (needed by the revision): one store lock covers every read-modify-write of the profile file (load with revision backfill, create, update, remove, upsert/import) and the in-memory revision map; mutations use an internal unlocked load under the same lock. The touched writes use the preserving replacement (`json_replace_preserving`, `src-tauri/src/file_storage.rs:159-205`) instead of the remove-first `.tmp` writer (`file_storage.rs:39-58,241-242`): a failed write leaves the previous file byte-for-byte and the revision map unchanged. A backfill that fails to persist returns an error. The lock is never held across network or Keychain work.
- R16 Conservative invalidation on observed profile changes (R10-P1-1): the frontend profile store (`src/stores/profile.ts`, every publication path: `loadProfiles`, `saveProfile`, removal, imports, MainScreen and `ConnectionScreen.onSaved` callers) keeps the last observed revision per profile. Before publishing any snapshot or single profile in which a profile's revision differs from the last observed one, or a profile is missing/removed, it synchronously bumps the generation (R5) of every tab of that profile. A successful local save/import/remove does the same immediately, before its own publication. This is equality-only and conservative: an out-of-order or stale snapshot can only cause an extra invalidation (and a reload of data), never authorize anything (R20 decides). Effect: results of work admitted before the change, completing afterwards, are not published; pending state is retired (R5); drafts are kept. Accepted window: until the frontend observes a change made elsewhere (another window/import it has not refreshed yet), already-loaded data may stay visible; any new backend work in that window is refused by R20 and triggers the reconnect message.
- R21 Dirty drafts and settings changes (R10-P1-2): (a) preflight: saving a profile (form, Save-only, Save+Connect) is refused while **any** tab of that profile has dirty row patches, object drafts or new-table drafts: "Save or discard the unsaved changes in the tabs of this connection before changing its settings."; (b) backstop for changes the preflight cannot see (imports, edits from another window, a stale runtime found by R20): a tab with dirty drafts never replaces its runtime (Reload/reconnect refused with "This tab has unsaved changes made against the previous settings. Copy or discard them, then reconnect."). Its drafts stay visible and copyable; discarding them through the existing flow enables Reload. Drafts created while a reconnect is awaiting make installation fail the same way (checked at install). No frontend revision comparison is needed for this rule.
- R20 Backend admission (replaces revisions 5–9's frontend ordering): every backend entry point that resolves a runtime by id for work on a target refuses a **stale** runtime with the error code `RUNTIME_STALE` (no details logged), by one helper `admit_runtime(state, connection_id) -> Result<EngineConnection, String>` that reads the runtime and its identity and compares the revision with the in-memory map (no file IO). Entry points (all current `state.connections` readers): `operations/dispatcher.rs:76` (queries, streams, explain), `commands/operation.rs:31,45`, `commands/sql_session.rs:35` (begin; an open session keeps its own connection), `commands/connection/version.rs:271`, `commands/mongo.rs:51`, `commands/cassandra.rs:34`, `commands/google_sheets.rs:16`, `commands/health_inspector/signal.rs:40`, `commands/ai_agent.rs:122,244`, `commands/ai_agent_data.rs:184`, and any other found during implementation (a test enumerates readers of `connections` and fails if one bypasses the helper; removal and listing are exempt). Admission is per request: work already admitted (a running query, an open restore session) is not interrupted by a later save. Runtimes whose identity is present with `profileId: null` are admitted as today; a runtime with **no** identity entry fails closed (`RUNTIME_IDENTITY_MISSING`).
  - Exempt readers (R10-P2-1), listed in the reader test: `connection_list`, `connection_remove`, the post-begin existence check in `commands/sql_session.rs:49` (existence only: a session already begun keeps working after a save, per the admitted-work rule; `sql_session_begin` itself is admitted at `:35`), and the AI run's tool-liveness closure (`commands/ai_agent.rs:129`, existence only). AI (R11-P1-1): the run is admitted at start (`ai_agent.rs:121-155`, before its executors are captured). AI tools do not read `state.connections`; they call executors captured at run setup, so per-tool admission is a **fallible admission port** handed to the tool registry with the executors: a `RuntimeAdmission` (backed by `admit_runtime` for the run's runtime id) checked **before each target-touching tool starts** in the catalog tools (`ai/agent/catalog/tools.rs:128-131,163-174,208-215`) and data tools (`ai/agent/data/tools.rs`), and **again after** `DataAccess::admit`'s asynchronous catalog/native-approval awaits (`ai/agent/data/tools.rs:103-153`) right before the executor runs. A refusal never touches the executor and ends the run with a terminal categorized failure (`ToolError::Stop` carrying `RUNTIME_STALE` / `RUNTIME_IDENTITY_MISSING`), not `ToolError::Failed` (which `ai/agent/run.rs:482-507` would hand back to the model and continue); the run's terminal event carries the category and the originating `{ runId, tabId, runtimeId, generation }` so the frontend applies R5 provenance. The existence-only liveness closure stays for cancellation; consent checks and save-triggered run cancellation stay unchanged and independent (consent is not revision authority). `ai_agent.rs:244` (`ai_agent_sql_safety`) and `ai_agent_data.rs:184` (`data_profile`, consent/status) are ordinary entry points: the former is admitted like other commands; the latter is a status path (unavailable with category). Existing sessions: execute/commit after a save continue on their own connection; a new session is refused.
  - Synchronization (R10-P2-2): the revision map is updated inside the R14 critical section after the file write succeeds (that update is the save's linearization point). `admit_runtime` takes no R14 lock: it clones the runtime under the connection-map guard, releases it, reads the identity, then the revision map, never holding two map guards at once and never across an await. Lock order: R14 never acquires the connection or identity maps; admission never acquires R14. A save that commits after admission read the old revision is "admitted before save" by definition.
  - Errors: `RUNTIME_STALE` / `RUNTIME_IDENTITY_MISSING` are propagated as typed categories through every wrapper: the AI binding lookup (`ai_agent_data.rs:182-187`) becomes a `Result` that propagates them; status-only paths (AI estimate, health/version status) report "unavailable" with the category for the UI. In the frontend, a stale error is handled only for the originating `{ tabId, runtimeId, generation }` (R5 provenance): a late stale error after a reconnect never invalidates the newer runtime.

### P1 — approval blockers

**R2-P1-1 — `{ engine, database, source }` is not sufficient target identity, and target equality is not runtime ownership.**

A saved profile can change host/port/SSH endpoint while retaining database `app`; old and new runtime identities remain equal. R4 can reuse the old runtime, and D3 cannot detect it. This is directly relevant to the form/profile-edit flows already included in R5. Non-database targets such as Turso URL and Sheets spreadsheet also cannot be distinguished by a nullable database field. The resolver returns only override/display/state, leaving intended normalized identity undefined; display must never be used for equality.

Specify a shared intended/runtime comparison contract with a nonsecret endpoint/target fingerprint or equivalent saved-profile target revision, captured before SSH rewrite. Preserve a separate display value and override source. Define whether `source` participates in equality (same database through default versus explicit override is the same location but has different D2 binding policy). Capture profile id and target revision in connect generations, not just `(tabId, override)`. Validate both tab runtime and table fallback. If tab runtime A and table runtime B are distinct ids on the same target, A must win: target equality permits safe fallback only when the authoritative runtime is absent; it does not permit parallel transaction/session authorities. Add endpoint-only edit, changed profile during pending connect, equal-target conflicting-id and non-database-target tests.

**R2-P1-2 — Form reuse still lacks a safe save/connect/commit protocol.**

“Connect through `connectTabOnce`” does not say how edited input gets saved and made visible before that helper reads tab/profile state. Keeping `profileSaveAndConnect` then connecting again opens an unwanted default runtime; calling the helper first uses old saved input. The current `onSaved` callback updates the shared profile only after the dialog has installed the runtime (`ConnectionFormDialog.tsx:180-230`, `ConnectionScreen.tsx:274-297`). A profile edit also affects sibling tabs, including default tabs with dirty drafts. “Save-only does not reconnect” does not define whether those tabs keep their old target, become blocked, or later reconnect with old drafts against the newly saved target.

Specify preflight dirty checks before changing effective target, save-only versus save+connect ordering, publishing the saved profile revision, forced acquisition rather than reusing an existing runtime, and atomic installation/invalidation after success. Preserve the old runtime/drafts on refusal/failure and remove superseded/orphan runtimes. Define sibling-tab behavior and supported-engine-to-supported-engine edits, not only unsupported engines. Recheck generation after every await. Tests must cover save success/connect failure, save-only followed by reload, endpoint/default-database edits, sibling dirty tabs, and closing the reused tab while saving/connecting.

**R2-P1-3 — R5 invalidation does not yet reach the actual metadata/load reuse layers.**

`sqlLoader.ts:213,454` globally deduplicates size/FK work by schema/table/engine, omitting runtime/target. Tabs on A and B loading `public.items` concurrently can receive A's metadata in B even with correct tab-owned connections. `sqlExecute.ts:63-73` writes columns after await and retains `curPrev.connectionId ?? connId`; its later signature checks do not protect every write or distinguish repeated identical signatures across target generations. Clearing the outer table entry cannot prevent these completions repopulating it. These files are absent from Phase 1.

Include runtime/generation provenance in lower-level in-flight keys and validate generation before metadata/cache/rows writes; invalidation must cancel or reject old completions rather than only clear maps. Explicitly include loader/executor/in-flight/store touch points. Also `cassandraLoader.ts:11-24` falls back to the saved profile keyspace when schema is empty/`default`, via `cassandraExecute.ts:21`; route that fallback through intended tab target, or prove the schema invariant prevents it. Add concurrent A/B same-schema/table tests with different foreign keys/stats and delayed old-target completion after reconnect; add the Cassandra fallback case. These are existing defects exposed by the promised target isolation, not proof of a newly implemented regression.

**R2-P1-4 — D4 can reinterpret legitimate default tabs as database tabs.**

A normal profile named `team · prod` produces a default tab with the same label (`openProfileTab.ts`); D4 sees a separator without the prefix `team · prod · ` and marks it ambiguous forever. Worse, renaming profile `team · prod` to `team` makes that old default tab exactly match `team · prod`; D4 migrates it to override `prod`, potentially opening a different database. Prefix matching alone does not establish legacy provenance.

At minimum, recognize exact equality with the current profile label as a normal default tab. Do not infer from arbitrary prefix-shaped historical labels without a provenance rule; fail closed or provide explicit target recovery when history cannot distinguish default versus legacy override. Define persisted migration/version or ambiguity representation: `{override:null,state:ambiguous}` must not become an ordinary default on a later restore after label inference is removed. Validate inferred SQLite full paths and unsupported engines; preserve draft ownership through failure/recovery. Add fixtures for profile labels containing separators, prefix-collision renames, empty overrides, unsupported explicit overrides, inactive tabs, stale window ids and failed-connect save/restart.

**R2-P1-5 — Phase 1's standalone safety claim contradicts D1/D3 and the stated session limitation.**

Phase 1 says a mismatch can only come from session-changing SQL “and is shown”. Initial input identity cannot detect `USE` at all; revision's Definitions correctly says so. Profile edits and stale cached ids can also produce mismatches. Display says mismatch blocks only in Phase 2, leaving a Phase-1 checkpoint with a warning but writes/reads still enabled, contrary to Goal/R5.

Either make both phases one release/approval unit (intermediate commits explicitly not shippable), or move minimal fail-closed admission into Phase 1 before consumers can use unknown/mismatched runtimes. Retain the exact Phase-2 operation matrix and post-await checks. State clearly that D1 shows startup target and D3 validates startup provenance, not mutable SQL session context; remove the claim that session-changing SQL mismatches are shown. No new session-tracking feature is required merely to correct that promise.
